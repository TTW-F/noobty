# ADR-0002: WebSocket 推送 + 历史追赶，而非轮询

- 状态：已接受
- 日期：2026-09-06

## 背景

Noobty 的核心体验是"设备在线状态实时可见、消息和来件实时到达"。实现方式必须在**轮询（polling）与订阅推送（push）**之间做显式选型——不能不加分析地默认其一。

## 备选方案分析

| 方案 | 延迟 | 空载开销 | 服务端状态 | 双向能力 | 评价 |
| --- | --- | --- | --- | --- | --- |
| 固定间隔轮询 | = 间隔（1–5 s） | 每设备每秒都在发请求，N 台设备 × QPS 常驻负载 | 无 | 无 | 实现最懒；延迟与开销不可兼得：想"实时"就得高频轮询，白白打满中枢 |
| 长轮询 (long-poll) | 低 | 空载 1 个挂起连接/设备 | 挂起请求管理复杂 | 无 | 是 2010 年代的兼容方案；在现代内网环境没有存在理由 |
| SSE (server-sent events) | 低 | 空载 1 个连接/设备 | 连接管理 | 单向（仅服务端→客户端） | ack、ping、M2 直转信令都要再开一条上行通道，两套连接维护两套断线逻辑 |
| **WebSocket (RFC 6455)** | 低（事件即时下发） | 空载 1 个连接/设备，零请求流量 | 连接注册表 | 原生双向 | 需要处理：有界队列、慢消费者、断线重连——均可工程化解决 |

## 决策

1. **推送**：每设备一条 WebSocket 长连接。在线状态、新消息、删除、确认全部由中枢主动下发（`hello` / `presence` / `message` / `message_deleted` / `file_deleted` / `message_acked`）。
2. **可靠性不靠推送兜底**：推送是 best-effort。每连接出站队列有界（128）；慢消费者被踢下线，重连后以 `GET /conversations/{id}/messages?after=<cursor>` 做历史追赶。**推送保实时，拉取保可靠**——这是 IM 领域的标准范式（与主流聊天系统一致）。
3. 应用层 `ping`/`pong` 帧保活（与 WebSocket 协议层的 ping/pong 相互独立），空闲连接不静默死亡。

## 后果

- 空载时中枢几乎零流量：N 台设备只有 N 条空闲 TCP 连接，而不是持续轮询请求。
- 延迟从"轮询间隔"变成"事件即发"。
- 必须正确处理重连语义（generation 计数防旧连接误报离线、重复会话踢旧、追赶游标）——这些在 `realtime.rs` 与 `api/ws.rs` 中实现并有 smoke 测试覆盖。
- 代价：中枢持有每设备 1 条连接与 1 个有界队列（可预估的内存上界）；浏览器与 Tauri WebView2 均原生支持 WebSocket，无兼容负担。

## 否决理由备忘

- 否决**轮询**：设备数量增长时负载线性放大，且"实时"与"省电省流量"根本冲突——这正是题目所说"不分析就盲目轮询"的反面教材。
- 否决 **SSE**：单向通道无法承载 ack/心跳/M2 直转信令，等于为上行再开一条通道，状态翻倍。
