# ADR-0003: 不引入 Centrifugo，单进程自研推送 + 学其恢复协议

- 状态：已接受
- 日期：2026-09-06

## 背景

M1 中枢已有自研 WebSocket 推送（`realtime.rs` + `api/ws.rs`，约 300 行）与 REST 历史追赶。评审中提出：手写实时层是「最容易藏 bug 的 20%」，而客户端自动重连/退避/重订阅原先只有契约、缺少可运行的参考实现；Centrifugo（Go 单二进制）可补这块，并内置 presence。

硬标准（产品与部署约束）：**高性能、高可靠、极低资源消耗**；部署为 Ubuntu 上单机 systemd，不用 Docker。

## 备选

| 方案 | 进程数 | 客户端健壮性 | 数据真相 | 运维面 | 评价 |
| --- | --- | --- | --- | --- | --- |
| **继续单进程自研** | 1 | 须自己写 Full Jitter 重连 + `after_seq` 追赶 | 唯一（SQLite + blob） | 最小 | 契合 LAN 家用规模 |
| 引入 Centrifugo | 2 | 官方 JS SDK 成熟 | 须关掉其 history，避免双真相；中枢仍持有历史 | +1 常驻进程；公网暴露面加倍 | 实时多一跳；换 SDK |
| MQTT (QoS1) | 2+ | Web 体验弱于 Centrifugo | 同上拆分 | Broker 运维 | 更偏物联网 |

## 决策

**不引入 Centrifugo。** 坚持单进程中枢；把成熟项目的机制**拆解后学进自研实现**，而不是集成整机：

1. **恢复游标** — 每会话单调 `seq`（对齐 Centrifugo channel `offset`），客户端重连用 `GET .../messages?after_seq=<n>`；推送仍 best-effort，历史是唯一真相（对齐「不开 Centrifugo history」）。
2. **客户端重连** — `web/src/lib/ws.ts` 为参考实现：25 s 应用层心跳；Full Jitter 指数退避 `randomInt(0, min(max, base·2^(n-1)))`（Centrifugo JS SDK / AWS 论文同款），避免多设备齐步重连。
3. **有界扇出** — 每连接出站队列 128；慢消费者踢除后靠 `after_seq` 补齐（已有）。
4. **自动化证明** — `scripts/smoke.sh` 覆盖「断线 → 离线消息未推 → `after_seq` 追赶恢复」。

不做 Centrifugo 的 `epoch`：我们的历史在 SQLite 持久化、不会「流重置」；删消息只造成空洞，`seq > n` 仍正确。若未来引入「整库清空 / 会话重置」，再补 epoch。

## 后果

- 零新运维面；空载仍是一个二进制 + N 条 WS。
- 客户端重连从「文档承诺」变为可引用代码 + smoke 证明。
- 须持续对照成熟实现做审计，禁止闭门造轮子式发明协议。

## 何时该反悔（触发条件）

出现任一情况，重新评估引入专用实时层（Centrifugo 或同等）：

1. **客户端重连缺陷反复出事故** — 生产或长期 soak 中因惊群/假死/漏追赶导致用户可见丢消息，且修自研成本高于接 SDK。
2. **连接规模超出家用 LAN** — 稳定在线设备 ≫ 家庭/小办公室量级（经验阈值：持续 > 200 并发 WS，或单机推送 CPU/内存成为主瓶颈）。
3. **需要跨节点扇出** — 多中枢或中枢与边缘拆分，单进程注册表不够。
4. **公网多租户** — v2 鉴权+暴露后，若实时通道与文件/API 进程隔离成为安全硬需求。

未触发前，默认保持本 ADR。
