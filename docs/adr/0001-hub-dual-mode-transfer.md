# ADR-0001: 中枢式双模式传输（寄存+直转），而非 P2P 直连

- 状态：已接受
- 日期：2026-09-06

## 背景

Noobty 需要在局域网内的多台 Windows PC 与安卓手机之间传输文件与文本。行业常规做法是 LocalSend 式的 P2P 直连（mDNS 发现、设备互传）。但本环境存在一个关键资产：局域网内有一台**常驻、局域网静态 IP 的 Ubuntu 服务器**，且项目长期目标是演进为局域网综合工具箱。

## 决策

所有传输经过中枢服务器，提供两种模式：

- **寄存（store-and-forward）**：文件落盘中枢，接收方任意时间取件，带过期与容量策略。
- **直转（streaming relay）**：收发双方同时在线时，数据流式穿过中枢实时送达，不等待整个上传完成，最少占用中枢磁盘。

私聊会话按目标设备在线状态在两模式间自动适配。

## 理由

- 寄存提供 P2P 做不到的**异步性**：发送方传完即可离开（手机传完就走，PC 随后取件）。
- 无需 mDNS 发现与配对，接入零门槛（浏览器扫码即用），避免了 P2P 方案在 Windows 防火墙、休眠、移动网络切换上的诸多调试成本。
- 中枢是常驻节点，天然成为将来工具箱功能（通知、剪贴板同步、设备管理）的底座。
- 直转模式弥补中枢方案的主要短板（双倍落盘与双倍时间），使在线互传仍接近线速。

## 后果

- 内网千兆下，寄存模式的实际吞吐约为线速一半（上传+下载各一次）——仍远快于原有微信方案，可接受。
- 中枢成为单点：中枢不可用则服务不可用。对家庭/个人场景可接受；服务由 systemd 自动拉起。
- 中枢磁盘需要寄存策略管理（30GB 上限 + 5 天保留，可配置）。
- 若未来需要离网直连（如中枢停机时应急），可作为 v2+ 的增强，不改变现有消息模型。

## 备选方案

- **纯 P2P 直连（LocalSend 模式）**：吞吐上限更高，但每台设备需常驻客户端、需发现配对、无法异步收发，且放弃中枢这一已有资产。
- **混合（信令 + 尽量直传）**：v1 复杂度最高；若直转模式实测满足速度需求，则无需引入 P2P 数据面。
